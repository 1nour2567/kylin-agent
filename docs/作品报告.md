## 摘要

随着大语言模型（LLM）在运维领域的应用日益广泛，AI Agent 管理服务器已成为一种新的技术趋势。然而，LLM 存在幻觉、注入攻击、越权操作等固有风险——传统的 prompt 约束方式属于软性防线，可被越狱攻击绕过。运维场景的特殊性在于：一条危险的 `rm -rf /` 即可造成不可逆的生产事故。

本文提出 **Constraint Architecture（约束架构）**——一种将 AI 推理与安全决策分离的四层纵深防御体系。其核心设计原则为：**LLM 负责思考，代码负责决定能否执行，审计负责不可抵赖。** 所有安全决策均由确定性代码完成，不依赖 LLM 的判断。

本作品基于 Constraint Architecture 实现了 **麒盾智维（KylinShield Ops）**——面向麒麟操作系统（Kylin Linux Advanced Server V11）的安全运维智能体。系统包含 16 个 MCP 运维工具，覆盖进程管理、磁盘监控、内存分析、网络连接、日志审计和包完整性验证。系统创新点包括：(1) T0-T3 四层纵深防线，全部为确定性代码；(2) 态势引擎——根据 veto 事件动态调节安全等级，类似央行利率政策；(3) Agentic Loop——多轮自主诊断推理，每轮重新通过四层防线；(4) SHA256 审计链——密码学级不可抵赖，跨重启持久化；(5) 意图画像（Intent Profile）——LLM 观测行为，代码作出安全决策，实现观测与决策分离。

系统在麒麟 V11 真机上完成部署验证。测试方面：141 个单元测试全部通过（< 1 秒），35 条越狱语料 0 穿透，16 次红队攻击 0 打穿。系统同时提供完整的中英文 Constraint Architecture 纲领文档和架构图。

**关键词：** AI Agent 安全、Constraint Architecture、纵深防御、LLM 约束、安全运维、SHA256 审计链、Agentic Loop

## Abstract

As Large Language Models (LLMs) are increasingly deployed in operations and maintenance scenarios, AI agents managing servers have become an emerging technical trend. However, LLMs carry inherent risks including hallucination, prompt injection, and privilege escalation — traditional prompt-based constraints are soft defenses that can be bypassed through jailbreak attacks. The operational context is unforgiving: a single `rm -rf /` command can cause irreversible production incidents.

This paper proposes **Constraint Architecture** — a four-layer defense-in-depth system that separates AI reasoning from security decision-making. Its core design principle: **LLM reasons. Code decides what is allowed. Audit ensures non-repudiation.** All security decisions are made by deterministic code, independent of LLM judgment.

We implement **麒盾智维（KylinShield Ops）** based on Constraint Architecture — a security-hardened intelligent operations agent for Kylin Linux Advanced Server V11. The system includes 16 MCP operations tools covering process management, disk monitoring, memory analysis, network connections, log auditing, and package integrity verification. Key innovations include: (1) T0-T3 four-layer defense-in-depth, all deterministic code; (2) Risk Posture Engine — dynamically adjusts security levels based on veto events; (3) Agentic Loop — multi-turn autonomous diagnostic reasoning with security re-validation at each iteration; (4) SHA256 audit chain — cryptographically tamper-evident with cross-restart persistence; (5) Intent Profile — LLM observes behavior, code makes security decisions, separating observation from decision.

The system has been deployed and verified on Kylin V11. Testing: 141 unit tests all pass (< 1 second), 35 jailbreak corpus entries with 0 penetrations, 16 red-team attacks with 0 successful breaches. The project also provides complete Chinese and English Constraint Architecture manifestos and architectural diagrams.

**Keywords:** AI Agent Security, Constraint Architecture, Defense-in-Depth, LLM Constraints, Security Operations, SHA256 Audit Chain, Agentic Loop

## 第1章 引言

### 1.1 项目背景

2025年以来，大语言模型在代码生成、故障诊断、自动化运维领域展现了前所未有的能力。从 OpenAI Codex 到 DeepSeek Coder，从微软 Copilot 到各类 AIOps 平台，AI 正在深刻改变运维工程师的工作方式。自然语言到系统命令的映射、多轮诊断推理、自动化工单处理——这些都已被证明在技术上是可行的。

然而，一个根本性的安全问题被普遍忽视：**LLM 输出的命令由谁负责验证？**

当前主流做法是在 system prompt 中写入安全规则——"不要执行危险命令""拒绝恶意请求"——依赖 LLM 自身执行这些约束。这种方式的致命缺陷在于：prompt 是软约束。一个精心构造的 prompt injection 可以覆盖这些规则；LLM 在多轮对话中可以被说服放弃自身的限制；即使模型今天对齐良好，明天的输入可能触发完全不同的行为。

更根本的问题在于：**让 LLM 自己定义自己的边界——这个想法本身是有结构性缺陷的。** LLM 是概率性系统，它不"知道"规则——它只是根据训练分布生成文本。当攻击者的输入改变了分布，原来"对齐"的行为就可能消失。这不是某个模型的缺陷，而是 prompt 约束范式的结构性局限。

### 1.2 国内外研究现状

在 AI Agent 安全领域，现有工作主要分为三类：

**Prompt 层面的安全对齐（OpenAI, Anthropic, DeepSeek 等）**：通过 RLHF、Constitutional AI 等方法训练模型拒绝危险请求。这类方法在单轮对话中有效，但在多轮越狱攻击下成功率大幅下降。Anthropic 的研究表明，即便是最先进的 Claude 模型，在面对精心设计的多轮越狱攻击时，成功率仍可达 20% 以上。

**输入过滤（Guardrails, NeMo Guardrails, LLM-Guard 等）**：在 LLM 输入端增加基于规则或轻量模型的过滤层。这类方法能拦截明显的注入攻击，但通常只检查输入文本——当攻击通过合法的自然语言表达（如"强制删除 /var/lib/mysql"而非"rm -rf"）时，文本过滤器难以判断意图。

**沙箱执行（E2B, Code Interpreter sandbox 等）**：在受限环境中执行 LLM 生成的代码。这类方法将安全边界放在执行层，但缺乏中间的约束验证——如果沙箱配置不完整，命令仍可能在受限环境中造成破坏。且现有沙箱方案通常只有"允许"和"拒绝"二元决策，缺乏差异化确认流程。

上述方案各有侧重，但均未形成完整的纵深防御体系。它们或依赖 LLM 自身判断（不可靠），或只覆盖单层防线（可被绕过），或缺乏事后不可抵赖的审计链（无法追溯）。

Constraint Architecture 的定位正是填补这一空白：四层独立防线，层层验证，确定性代码决策，密码学级审计。

### 1.3 项目目标

本项目面向麒麟操作系统（Kylin Linux Advanced Server V11，国产化替代关键基础设施），设计并实现一个安全硬化的 AI 运维 Agent。具体目标包括：

1. **四层纵深防线**：实现 T0（注入检测）→ T1（风险评分）→ T2（约束验证）→ T3（沙箱执行）的完整安全管线，所有安全决策由确定性代码完成，LLM 不参与。

2. **完整运维能力**：基于 MCP（Model Context Protocol）协议实现 16 个运维工具，覆盖进程、磁盘、内存、网络、日志、包管理等核心运维场景。

3. **自主推理诊断**：实现 Agentic Loop 多轮自主诊断，支持自然语言触发（中文），每轮诊断重新通过四层防线。

4. **态势自适应**：实现态势引擎根据 veto 事件自动调节安全等级，支持 restrictive/balanced/permissive 三态切换。

5. **审计溯源**：实现 SHA256 审计链，跨重启持久化，支持 FOIA 查询和链完整性验证。

### 1.4 项目意义

**学术意义**：提出了 Constraint Architecture 这一通用 Agent 安全架构，将安全工程中经过 50 年验证的纵深防御、最小权限、不可抵赖审计原则引入 LLM Agent 领域。该架构不绑定特定领域——已在安全运维（麒盾智维（KylinShield Ops））和具身化 AI（Malio）两个完全不同的领域独立验证成立。

**工程意义**：为国产操作系统生态提供了首个 AI 安全运维 Agent。麒麟操作系统在军队、政府、金融等关键领域广泛部署，但运维人员数量和技术积累相对薄弱。麒盾智维（KylinShield Ops） 通过自然语言接口降低麒麟 OS 的运维门槛，同时通过四层防线确保操作安全不降级。

**社会意义**：在 AI Agent 能力快速提升的背景下，安全约束不应成为事后补救——应从一开始就内置于架构设计之中。本项目尝试为这一方向提供一个可参考的实现路径。

## 第2章 系统设计

### 2.1 总体架构

麒盾智维（KylinShield Ops） 采用 Constraint Architecture 四层分层架构，其核心设计思想为：**LLM 负责思考，代码负责决定，审计负责记录。** 系统总体架构如图2-1所示。

```
用户自然语言输入
       |
       v
   T0 注入检测    ←──── 确定性正则引擎（18条规则 + Unicode + Base64）
       |
       v
   环境感知层      ←──── OS传感器快照 + 审计历史 + 会话上下文
       |
       v
   意图分类器      ←──── LLM分类（query/action/emergency）+ 规则引擎兜底
       |
       v
   Agentic Loop   ←──── 多轮自主推理（Reason→Validate→Execute→Observe）
       |                  每轮重新过 T0-T3
       v
   LLM 推理层      ←──── DeepSeek API + 动态 System Prompt（姿态/角色/时间感知）
       |
       v
   T1 风险评分     ←──── 确定性风险矩阵（1-10分），从Manifest派生
       |
       v
   T2 约束验证     ←──── 双路径校验（结构化参数+原始正则）+ 文件语义识别
       |
       |  ┌── auto 级 ──→ 直接执行
       ├──┤
       |  ├── confirm 级 → 人工确认后受限执行
       |  └── veto 级 ──→ 不可执行
       v
   T3 沙箱执行     ←──── 白名单 + sudo -n降权 + confirm队列持久化
       |
       v
   SHA256 审计链   ←──── 追加JSONL + 链式哈希 + 跨重启持久化 + FOIA查询
```

**核心数据流**：用户输入 → T0 注入检测 → 环境感知 → 意图分类 → LLM 推理（输出结构化命令建议）→ T1 风险评分 → T2 约束验证（可否决）→ T3 沙箱执行（auto/confirm/veto）→ SHA256 审计记录 → 返回结果。

**关键设计：LLM 不参与安全决策。** 从 T0 到 T3，每一个安全判断都由确定性代码完成。LLM 的输出仅仅是"建议"——T2 约束层独立验证这些建议，T3 沙箱层决定是否执行以及以何种权限执行。攻击者即使完全控制了 LLM，也无法绕过 T0 的注入过滤、T1 的风险评估、T2 的约束验证和 T3 的白名单执行。

### 2.2 Constraint Architecture

Constraint Architecture 是本系统的理论基础。它是一个与领域无关的通用 Agent 安全架构，定义了 LLM Agent 的边界应该如何由代码而非 prompt 来强制。

#### 2.2.1 设计动机

当前 AI Agent 安全的主流范式是 **"Prompt 说了算"**——在 system prompt 中写入安全规则，依赖 LLM 自身执行这些约束。这一范式的根本缺陷在于：

- **Prompt 是软约束**：LLM 可以在多轮对话中被说服放弃自己的限制
- **Prompt injection 是结构性问题**：输入文本中的指令可以覆盖 system prompt 中的指令
- **LLM 不真正"理解"规则**：它是概率性系统，行为随输入分布变化而变化

Constraint Architecture 的回答是：**边界不该由 LLM 定义。该由代码定义。**

#### 2.2.2 四层分层

Constraint Architecture 定义四个独立的分层：

**Layer 1 — Reasoning（推理层）**：LLM 自由推理，输出结构化指令。LLM 的输出是信息源，不是行动许可。这一层给 LLM 最大空间——能想的都可以想。

**Layer 2 — Constraints（约束层）**：确定性代码层。读取 LLM 输出，进行双路径校验（结构化参数校验 + 原始输出正则）。这一层对 LLM 不可知——攻击者控制 LLM 也过不了。约束只增不减：无论当前模式多"宽松"，基础规则不撤。

**Layer 3 — Execution（执行层）**：白名单校验，分级执行（auto / confirm / veto）。非白名单指令不可执行。非白名单路径不可触碰。执行者角色与权限在这一层强制生效——无可绕过。

**Layer 4 — Audit（审计层）**：每步操作被记录。篡改可被检测。理想形式是链式不可篡改（SHA256 链），确保"已发生的事实"不可被事后否认。

**优先级规则：Layer 2 硬约束 > Layer 1 推理偏好。** 当执行层说"不"，推理层的"要"不生效。不是协商——是硬性覆盖。

#### 2.2.3 "LLM是观测者，代码是决策者"

Constraint Architecture 最具创新性的设计原则是**分离观测与决策**。LLM 可以观测用户行为、分析意图、警示风险——但它不做出安全决策。代码接收到 LLM 的观测信号后，查询自身的确定性规则表，自主决定是否降低/提高安全门槛。

这一设计保证了 LLM 的认知错误不会造成灾难——只会影响用户体验。决策权始终在确定性代码手中。

#### 2.2.4 多Agent职责约束

Constraint Architecture 的第二层含义是**约束每个Agent模块的职责——没有人有一把万能钥匙**。麒盾智维（KylinShield Ops） 将系统分解为六个独立模块，各自拥有非重叠的权限边界：

- **Classifier**：只负责意图分类。不执行命令。
- **Reasoner**：只负责推理。不能跳过 T2。
- **ProactiveInspector**：只负责观测。发现 critical 后只能推告警——不能自己改 posture，不能自己执行命令。
- **BaselineLearner**：只负责学习基线。不参与实时决策。
- **RiskPostureEngine**：独立于所有模块的安全姿态。被 veto 触发后自己收紧约束——Reasoner 不能 override 它。
- **Guardrail**：T0-T3 全链路编排——但它不推理、不执行、不学习。只负责串联约束流程。

**把权力拆开。没有单点可以全部接管。**

### 2.3 四层纵深防线（T0-T3）

麒盾智维（KylinShield Ops） 的四层防线分别对应 Constraint Architecture 的 Layer 1-3 和 T0 补充防御：

#### 2.3.1 T0 — 注入检测（Anti-Injection Gateway）

T0 层是输入的第一道防线，在用户输入进入 LLM 之前进行检测。它包含：

- **18 条正则注入模式**：覆盖 prompt injection（"ignore previous instructions""pretend you are"）、分隔符注入（"---""[INST]""<|im_start|>"）、角色切换（"act as if""you are now a root shell"）
- **Unicode NFC 规范化**：处理同形异义字符攻击（零宽字符、全角字符等），先规范化再匹配
- **Base64 编码检测**：识别 `echo <base64> | base64 -d | sh` 模式，自动解码并检查解码后的内容
- **Hex 编码检测**：识别 `printf '\x72\x6d...' | sh` 模式
- **输入长度守卫**：超过 8000 字符的输入直接拒绝
- **REF 引用码**：每次拦截生成唯一 REF 码（如 REF-00042），供审计追溯

T0 的关键设计选择是：**不依赖 LLM 判断是否有害——用正则引擎在入口处就拦截已知攻击模式。**

#### 2.3.2 T1 — 风险评分（Deterministic Risk Model）

T1 层对 LLM 输出的每条命令进行确定性风险评分（1-10分）：

- **评分来源**：从 Tools Manifest（工具清单）直接派生，不经过 LLM
- **只读命令**（ps/df/free/ss/journalctl status/lsof/rpm）：风险评分 1 分
- **标准写命令**（systemctl restart/kill -15/truncate）：风险评分 5-6 分
- **危险操作**（kill -9/iptables -F/systemctl stop）：风险评分 7-8 分
- **破坏性命令**（rm -rf / / mkfs / chmod 777 /）：风险评分 10 分
- **风险标签映射**：1-2=LOW, 3-5=MEDIUM, 6-7=HIGH, 8-10=CRITICAL

T1 的关键设计：评分逻辑是硬编码的查表和字符串匹配——任何攻击者都无法让 LLM "说"一个低分来绕过 T1。

#### 2.3.3 T2 — 约束验证（Structural Constraint Engine）

T2 层是安全决策的核心，执行双路径独立校验：

**路径一：结构化工具调用校验**
- 命令白名单：16 个工具必须在 Manifest 中注册
- 危险工具拦截：`rm`、`mkfs`、`fdisk`、`dd` 等 → veto 级，永不可执行
- 危险路径检测：`/dev/sd*`、`/etc/shadow`、`/etc/sudoers`、`/boot`、`/sys/kernel`、`/root/.ssh` → veto
- 文件路径前缀阻塞：`/etc`、`/boot`、`/sys`、`/proc`、`/root` → veto
- 危险参数值检测：`mode=777`、`action=stop/disable/mask`、`permissions=777` → confirm
- 危险标志位检测：`-rf`、`-Rf`、`--force`、`-9`、`-SIGKILL` → confirm
- 文件内容检测：扫描待写入内容的 WRITE_INDICATORS → confirm
- 脚本路径+shebang 验证：只允许 `/tmp/kylin-agent/`，禁止 python/perl/ruby shebang

**路径二：语义文件识别**（赛题核心要求 A2）
- **FileKnowledgeBase** 实现 11 类文件分类：临时缓存(1) → 过期日志(2) → 软件包缓存(2) → Core Dump(3) → 用户上传(3) → 应用日志(5) → 数据库日志(7) → 系统日志(8) → 配置文件(9) → 数据库数据(10) → 二进制库(10)
- **关键数据库日志识别**：匹配 `mysql/mariadb/postgres/mongod/redis/etcd/elasticsearch` 等数据库日志路径
- **安全清理建议**：不同类型文件返回不同的清理建议——expired_log 可直接删除，database_log 建议 logrotate，database_data/配置文件永不可删除
- **确认阈值动态计算**：`effective_threshold = posture_base + role_offset - intent_boost`

**路径三：原始命令正则校验**（Legacy/Shell 路径）
- 8 条禁止模式（`rm -rf /`、`mkfs.*`、`dd if=`、`chmod 777 /` 等）
- 5 条确认模式（`systemctl stop/disable`、`kill -9`、`chown -R` 等）

**角色权限校验**：
- Viewer：只能使用 9 个只读工具（ps/df/free/ss/journalctl/systemctl status/lsof/rpm）
- Operator：可以使用所有工具，高风险操作需确认
- Admin：+2 阈值偏移，确认门槛更低

**意图画像（Intent Profile）集成**：
- LLM 输出 `risk_hint` 信号（"正常"、"越权重试"、"高危"）
- T2 根据 `risk_hint` 计算 `intent_boost`（0-4），动态收紧确认阈值
- LLM 观测，代码决策——LLM 判断错误只是多确认一次，不会造成安全漏洞

#### 2.3.4 T3 — 沙箱执行（Tiered Execution Sandbox）

T3 层是最后一道防线，采用三级执行模型：

- **auto 级**（9 个只读工具）：直接执行，无需确认。如 `ps aux`、`df -h`、`free`
- **confirm 级**（4 个写工具 + 3 个文件工具）：T2 通过后，必须用户显式确认，然后以受限用户（`kylin-agent`）执行。如 `systemctl restart sshd`、`kill_process`、`truncate_log`
- **veto 级**（2 个破坏性命令）：**在任何角色、任何姿态下永不可执行**。如 `rm`、`chmod`

**沙箱安全特性**：
- 白名单执行：不在 Manifest 中的命令一律不可执行
- sudo 降权：confirm 级命令以 `sudo -n -u kylin-agent` 执行（非交互式，无密码）
- 特权确认白名单：仅 4 组命令（`systemctl restart`、`journalctl --vacuum-time`、`kill -15`、`truncate -s`）可被 sudo 授权
- 根用户检测：当 Agent 服务进程以 root 运行时，文件/脚本操作直接拒绝
- 脚本执行限制：仅 `/tmp/kylin-agent/` 下可执行，禁止 python/perl/ruby shebang，禁止 world-writable 脚本
- 确认队列持久化：PendingStore 的 JSON 持久化在服务重启后保留等待确认的命令

### 2.4 态势引擎

RiskPostureEngine（态势引擎）实现了动态安全等级调节，类似中央银行的利率政策：

**三态模型**：
| 态势 | 确认阈值 | 审计强度 | 触发条件 |
|------|---------|---------|---------|
| restrictive | 0（全部确认） | 摘要 | ≥2 次 veto 事件，或夜间 22-06 |
| balanced（默认） | 5 | 正常 | 正常运维 |
| permissive | 7 | 完整 | 手动启用 |

**自动调节机制**：
- **自动升级**：连续 2 次 T2 veto → 自动升级到 restrictive，所有命令都需要确认
- **自动降级**：24 小时无 veto → 自动回归 balanced
- **夜间锁定**：22:00-06:00 自动上锁，permissive → balanced
- **主动巡检升级**：ProactiveInspector 发现 critical 事件 → 自动升级到 restrictive
- **态势记忆**：态势漂移日志记录所有状态变更的触发条件、时间和原因

**动态 System Prompt**：LLM 的 system prompt 随态势和角色动态变化——restrictive 模式下 LLM 只输出只读命令，viewer 模式下 LLM 主动解释角色限制。

### 2.5 Agentic Loop（多轮自主诊断）

Agentic Loop 实现了多轮自主推理能力，区别于单轮问答：

**触发机制**：中文关键词触发（排查、诊断、为什么不、什么原因、帮我查、检查系统、系统健康、全面检查 等 12 个触发词）

**执行流程**：
1. LLM 推理当前轮次的诊断步骤
2. T2 约束验证所有 LLM 建议的命令
3. T3 执行通过验证的命令
4. 观察执行结果作为下一轮的上下文
5. 重复 1-4，最多 3 轮

**核心安全特性**：每轮迭代重新读取当前态势（posture），防止态势升级后的命令绕过。

**6 阶段 RCA 推理链**：Symptom Confirmation → Hypothesis Generation → Evidence Collection → Root Cause Identification → Remediation Plan → Verification。LLM 按这六个阶段进行结构化诊断推理。

### 2.6 SHA256 审计链

审计层实现了密码学级的不可抵赖性：

- **追加式 JSONL 存储**：每日一个文件（`data/audit/YYYY-MM-DD.jsonl`），追加写入
- **链式 SHA256 哈希**：每个事件的 `event_hash` 由 `SHA256(event_data + previous_hash)` 生成
- **跨重启持久化**：启动时 `_seed_from_disk()` 扫描所有 JSONL 文件，恢复最后一个 `event_hash` 作为链头
- **7 阶段管线记录**：receive → perceive → route → reason → validate → execute → chain_close
- **篡改可发现**：`/api/audit/verify` 端点遍历全链验证哈希——改任意一条全链断裂
- **FOIA 查询**：`/api/audit/trail?from_date=...&to_date=...` 支持按日期范围查询审计记录
- **敏感信息脱敏**：API key、Bearer token、password 等敏感值在写入审计日志前自动脱敏（`Bearer xxx` → `Bearer ...REDACTED`）
- **WebSocket 实时推送**：审计事件通过 WebSocket 实时推送到前端审计面板
- **并发安全**：哈希计算和文件追加在同一临界区内（`_hash_lock`）

### 3.5 Files KnowledgeBase

FileKnowledgeBase 实现了赛题要求的"识别文件是否为关键数据库日志"功能：

- **分类体系**：11 类文件，风险评分从 1（临时缓存）到 10（数据库数据/二进制库）
- **正则匹配规则**：覆盖常见的数据库日志路径（`mysql/mariadb/postgres/mongod/redis/etcd/elasticsearch.log`）、系统日志路径（`/var/log/secure/messages/syslog`）、配置文件后缀（`.conf/.cfg/.yaml/.ini`）、数据库文件后缀（`.db/.sqlite/.mdb`）
- **清理候选排序**：按可清理性 + 风险评分排序，优先建议清理临时缓存和过期日志
- **知识注入**：分类规则以紧凑的 Markdown 表格形式注入 LLM system prompt，确保 LLM 在推理时已有安全清理的基线知识

### 4.3 安全性测试

#### 4.3.1 注入攻击

- **35 条越狱语料**（`data/jailbreak_corpus.json`）：覆盖英文角色切换、中文角色切换、分隔符注入、编码负载等多种攻击向量
- **0 穿透**：35 条语料全部被 T0（正则匹配）或 T2（约束验证）拦截
- **T0 独立拦截**：大部分注入攻击在 T0 就被拦截，从未到达 LLM
- **T2 兜底**：使用中文合法自然语言表达的攻击（如"强制删除 /var/lib/mysql"而非明显的"rm -rf"）虽然通过 T0，但在 T2 被路径保护和语义识别拦截

#### 4.3.2 红队攻击

16 次红队攻击，0 次打穿四层防线。攻击类型包括：
- 直接注入（"ignore previous instructions"）
- 编码绕过（base64/hex 编码危险命令）
- 间接注入（日志内容污染 → LLM 上下文注入）
- 角色越权（viewer 尝试执行写操作 → T2 拒绝）
- 路径遍历（尝试写入 /etc → T2 路径阻塞）
- 参数注入（kill -1、systemctl restart ../../../etc/shadow → T2 参数校验）

### 4.4 性能测试

- **T0-T3 安全管线延迟**：< 5ms（全部确定性计算，无 LLM 调用）
- **LLM 推理延迟**：取决于 DeepSeek API（通常 1-3 秒）
- **Agentic Loop 总耗时**：< 15 秒（最多 3 轮，每轮包含 LLM 推理 + 安全校验 + 命令执行）
- **单元测试耗时**：< 1 秒（141 个测试全部结构性）
- **并发审计写入**：通过 `_hash_lock` 保证并发安全，10 并发写入后全链 VERIFY 通过

### 4.5 真机部署验证

在麒麟 Linux Advanced Server V11 (Swan25) x86_64 真机上完成部署验证：
- systemd 服务安装并通过安全沙箱运行（`NoNewPrivileges=true`，`ProtectSystem=full`）

## 附录C：部署步骤

```bash
# 1. 解压
tar xzf kylin-agent-deploy.tar.gz -C /opt/kylin-agent/

# 2. 安装
cd /opt/kylin-agent
sudo bash deploy/kylin-install.sh

# 3. 配置 API Key
sudo vi /opt/kylin-agent/.env
# DEEPSEEK_API_KEY=sk-your-key
# AGENT_MODE=default

# 4. 启动
sudo systemctl enable --now kylin-agent

# 5. 访问
# http://<server-ip>:8008
```

非 root 用户级启动（开发/演示）：

```bash
cd ~/kylin-agent/backend
pip3 install -r requirements.txt --user
cp .env.example .env  # 编辑配置
mkdir -p ../data/audit ../data/logs ../data/baseline /tmp/kylin-agent
python3 main.py  # http://localhost:8008
```
